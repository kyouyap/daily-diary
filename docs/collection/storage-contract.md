# 日別JSONと収集結果の保存仕様案

更新日: 2026-10-17。本人が本仕様と更新計画を承認済み。合意した方針は[条件整理](decisions.md)を参照する。仕様の承認は、動作確認済みの実装であることを意味しない。

## 1. 保存場所と責任

既存のignore対象 `.daily-diary-runtime/` を保存先とする案。Gitへ入れるのは仕様・処理・架空データによるテスト・設定例だけとする。

```text
.daily-diary-runtime/
  config.json
  records/YYYY-MM-DD/x/account-a.json
  records/YYYY-MM-DD/youtube/account-a.json
  records/YYYY-MM-DD/langfuse/self.json
  records/YYYY-MM-DD/computer-history/self.json
  records/YYYY-MM-DD/screentime/self.json
  state/targets/<source>/<account>.json
  pending/
  backups/
  collection.lock
```

収集スキルはChrome・既存接続を読み、収集結果JSONを返す。保存処理はネットワーク・ブラウザ・認証情報へアクセスせず、渡されたJSONの検証・保存・進捗管理を行う。実設定のアカウント識別情報を公開用の設定例へコピーしない。

フォルダは所有者だけが使える権限、ファイルも所有者だけが読み書きできる権限とする案。保存先にシンボリックリンクがある場合や、管理フォルダ外へ出るパスは拒否する。日付は厳密な `YYYY-MM-DD`、sourceは上記5種類のみ、accountは小文字英数字とハイフンによる別名とする。実際のハンドルをファイル名に使わない。

## 2. 対象期間

- 日付境界はAsia/Tokyo。対象期間は開始を含み、終了を含まない。
- 通常は実行日の3日前0時から実行時点まで。例として10月17日7時の実行なら10月14日0時〜17日7時を対象にする。
- 初回の「過去30日分」は実行日の30日前0時から実行時点までとする案。10月17日なら9月17日0時からとなる。
- 当日の確認は実行時点までの暫定結果であり、一日全部を確認済みにはしない。後から来る記録は通常の再取得で追加する。
- 長期停止時は最後の確認範囲と未確認範囲を使って追加回収する。初回の開始日より前へ自動拡張しない。古い記録が取得できない場合は欠落を残す。
- 長期停止分は一度に全期間を要求せず、古い日付から最大7日分ずつに分割する案。通常の直近分も別に取得し、過去分の失敗で直近分を止めない。無人実行一回あたりの回収量・実行時間上限は実行経路の検証後に決める。

## 3. 収集スキルが返すJSON

一つのsource・account・取得要求につき一つの結果を返す。入力文字列はUTF-8のJSONオブジェクト。未知のschema_version、不正な型、対象外資料、期間やアカウントの不一致は取込前に拒否し、既存ファイルを変更しない。

| 項目 | 型・意味 |
|---|---|
| `schema_version` | 整数。初版は `1` |
| `batch_id` | UUID文字列。同じ取得結果の再取込では同じ値を使う |
| `source`, `account` | 許可された資料名、設定済みアカウントの別名 |
| `observed_identity` | 実際に閲覧・取得した本人の識別子。configのidentityと照合する必須文字列 |
| `requested_range` | `start`, `end`。タイムゾーン付きISO日時 |
| `observed_at` | 読取時点のタイムゾーン付きISO日時 |
| `status` | `success`, `partial`, `failed`, `login_required`, `environment_unavailable` のいずれか |
| `coverage` | 確認できた区間の配列。各要素は `start`, `end`, `evidence` |
| `records` | 下記の記録オブジェクトの配列 |
| `issues` | `code`, `retryable`, `range` を持つ配列。rangeは期間不明ならnull。生の例外・ページ本文・資格情報を診断文へ入れない |

`evidence` は `method` と `reference` の文字列を持つ。ページ終端・対象期間外への到達・API全ページ完了など、確認方法とその参照を記す。資格情報付きURLや画面全体は使わない。主張の根拠を残す項目であり、スクリプトがブラウザの全件取得を独力で証明するものではない。

`success` は要求全体を確認できた場合だけ。記録ゼロの成功は `records=[]` と要求全体のcoverageを持つ。`partial` は読めた記録と確認範囲だけを返す。ほか3状態は記録とcoverageを空にする。途中まで読めてから認証切れ等になった場合は `partial` と該当issueを返し、対象を保留する。

coverageの区間は要求内で、重複・順不同は正規化する。証拠のない空白区間は埋めない。記録の最古・最新日時だけでcoverageを生成しない。Xの通常投稿だけ確認した場合など、要求した種類を全部確認できていなければ全体のsuccessにしない。

## 4. 記録の項目と日時

| 項目 | 型・意味 |
|---|---|
| `kind` | 資料ごとの記録種別 |
| `external_id` | 投稿ID・動画ID・observation ID・イベント識別子などの文字列 |
| `event_time` | `value`, `precision`, `timezone`, `observed_label` のオブジェクト |
| `content_time` | 元コンテンツの日時。同じ構造。なければnull |
| `url` | 出典URL。URLがない資料はnull。認証情報を含めない |
| `data` | 下記の資料別項目だけを持つオブジェクト |

`precision` は `second`, `minute`, `day`, `unknown`。秒・分ならvalueは明示的なオフセット付きISO日時、dayなら日付、unknownならnull。日付表示だけを0時の出来事へ変換しない。timezoneが確定しない場合はnullとし、元の表示はobserved_labelへ残す。実施日を日本時間へ確定できない記録は初回取得日に保存するが、その日の行動の根拠にしない。

保存処理が `record_key`, `storage_date`, `first_observed_at`, `last_observed_at` を付ける。収集側からこれらを指定して上書きできない。初回日時は初回読取のobserved_at、再取得時はfirstを維持してlastだけ更新する。既に日時不明として保存した記録に後から正確な日時が見つかった場合はevent_timeを補足し、storage_dateとfirstは維持する。日記側はstorage_dateだけでなくevent_timeも参照する。

| 資料 | kindと保存する最小項目 | 重複の単位 |
|---|---|---|
| X | `post`, `reply`, `quote`, `repost`。本文、本人の著者識別子、返信先ID、引用元・共有元のIDと著者・画面に表示された本文 | 対象アカウント＋種別＋投稿ID。repostは元投稿ID。元投稿と共有日時を分ける |
| YouTube | `playback`。動画名、チャンネル、Shorts等の区分、表示された再生日時。動画全長は任意の参考値 | アカウント＋確定した再生日＋動画ID。不明日は初回取得日に固定 |
| Langfuse | `conversation`。本人ID、observation/trace/session ID、本人の入力とAIの出力。各本文は別項目 | アカウント＋observation ID |
| PC記録 | `activity`。イベントIDまたはセグメントID＋行番号、アプリ、観測した操作種別、必要な範囲のウィンドウ名・URL・観測内容 | アカウント＋イベント識別子 |
| Screen Time | `usage`。エクスポート世代とハッシュ、対象日・端末・アプリの利用秒数。アプリ内の行動は推定しない | 日付＋端末＋アプリ。訂正集計は同じ項目を置換 |

YouTubeは同日の同じ動画を一つの記録にまとめ、区別できる再生日時を `data.observed_playback_times` 配列へ重複なく保持する案。別日の同じ動画は別記録。同日反復の全再生回数は作らず、この配列の要素数も再生回数とは呼ばない。時刻の精度が改善しても動画の日別キーは変えない。不明日から確定日へ改善した場合は元の記録との照合根拠がある場合だけ統合し、推測で同一視しない。

Xの既存本文を編集追跡しない。Langfuseの後着した出力等は同じIDの未取得項目を補足できる。Screen Timeは読取成功した固定世代の集計だけを更新し、世代が読めない場合にゼロへ置換しない。日別集計は0時から対象日内の終了時刻までの累積値に限定し、その終了時刻をmeasurement_endとして保存する。短い古い取得区間で長い既存集計を上書きしない。部分日からの追加回収は0時から読み直す。端末をまたいだ利用秒数を一日の実時間として合算しない。

引用先・返信先の追加巡回、画像・動画ファイル保存は初版に含めない。AIへの入力は合意したCodex内の収集・振り返りに限り、保存スクリプトからAI APIを呼ばない。PC記録やScreen Timeの生ログ全体をCodexへ一括投入しない。PC記録は対象期間・必要項目に絞り、Screen Timeは日・端末・アプリ別の集計と参照情報を使う案。

## 5. 日別JSONと進捗

日別ファイルは `schema_version`, `date`, `source`, `account`, `records`, `updated_at` を持つ。収集結果をそのまま日別ファイルとして保存せず、記録を日付で振り分ける。日付不明の初回取得日と資料をまたぐ出典は維持する。

進捗ファイルは `schema_version`, `source`, `account`, `initial_start`, `covered_ranges`, `last_attempt`, `last_success`, `blocked_reason`, `record_index`, `applied_batches`, `notification_state` を持つ。record_indexは全日付を横断したキーと保存日の対応、applied_batchesは取込済みbatch_idと内容ハッシュの対応。進捗だけから投稿本文を読めない構成にする。

同じbatch_id・同じ内容の再取込は何も増やさない。同じIDで内容が違えば拒否する。後続の別batchが同じ記録を読んでも、資料ごとのキーで統合する。取得失敗や画面から見えなくなったことを理由に既存記録を削除しない。

通知状態は `issue_code` と対象を照合し、同じ問題の継続では通知要求を増やさない。解消後に再発した場合は新しい状態変化として扱う。CLIは通知すべき状態を返すだけで、アプリ通知の送信経路は未検証のまま分離する。

## 6. 保存途中の停止と競合

1. 保存・読取で共通のロックを取り、未完了の保存があれば先に回復する。ほかの保存・読取が実行中なら `busy` を返す。このロックはブラウザ操作全体の排他を実現するものではない。収集全体の二重起動防止はTask 6で実行経路と一緒に扱い、それまでは手動収集を直列で行う。
2. 入力を全件検証し、更新後の日別JSON・進捗JSONを作る。途中で不正な記録が見つかれば、そのbatch全体を拒否する。
3. 更新後の各ファイルとハッシュをpending内の一時トランザクションへ書き、ファイル・ディレクトリを同期したうえで、回復可能な完成状態へ原子的に切り替える。
4. 日別ファイルを一時ファイルから置換する。進捗は最後に置換する。すべて同期できた後にpendingを除去する。
5. 途中停止後は同じ完成済みpendingを再適用して完了させる。回復前に新しい取込・日記読取・バックアップは行わない。完成前の一時領域は成果にしない。

pendingのハッシュ不一致・破損があれば自動で捨てず、回復が必要な状態として止める。進捗の破損も空の初回状態へ置換しない。OS停止・競合・日別保存後かつ進捗保存前の停止を架空データで検証する。

## 7. バックアップと復旧の提案

具体値は今回の提案: 最初の正常な保存後に一回、以後は更新があった日の最初の正常な取込後に一回、最大7世代を `.daily-diary-runtime/backups/` に保存する。取得失敗・回復未完了の状態を正常世代として保存しない。ここでいう正常な取込は保存処理の成功であり、全資料の取得成功を条件にしない。

ロック下で日別記録・進捗・実設定の整合したスナップショットとハッシュ一覧を作る。認証キー・Cookie・外部の元データ・既存Screen Time DBは含めない。世代の完成後に古い世代を整理する。元データの無期限保持と、バックアップの世代数制限を区別する。

復旧は新しい空フォルダへ展開し、ハッシュ・日別ファイルと進捗の対応を確認する。稼働中の保存先やScreen Time環境を上書きしない。同じMac内のためMac自体の故障・紛失への対策にはならない。

## 8. 実装時の関数とCLI

すべて標準ライブラリで扱えるdict/list/Pathを入出力とし、処理結果を理由付きで返す。

| 場所・関数 | 入出力と副作用 |
|---|---|
| `records.validate_batch(batch: dict, config: dict) -> dict` | 設定済み対象・型・範囲・資料別項目を検証し、正規化したbatchを返す。I/Oなし。不正ならValueError |
| `records.record_key(source: str, account: str, record: dict) -> str` | 上記資料別のキーを生成。I/Oなし。YouTubeは既存索引の照合後に確定したstorage_dateを持つ正規化済みrecordを受ける |
| `state.plan_collection(config: dict, states: list[dict], now: datetime) -> list[dict]` | 資料・アカウント・通常/回収の別・対象期間を持つ要求一覧を返す。I/Oなし。保留も理由付きで残す |
| `store.import_batch(root: Path, batch: dict) -> dict` | ローカル設定を読み、ロック・回復・検証・保存を行う。status、変更件数、未確認範囲、通知要求を返す。ブラウザ操作・通信なし |
| `store.recover(root: Path) -> dict` | ロック下で未完了トランザクションを回復。根拠なく欠落ファイルを生成しない |
| `store.read_day(root: Path, date: str) -> dict` | ロック・回復後に対象日の記録と対象別取得状況を返す。外部資料は取得しない |
| `backup.create_backup(root: Path) -> dict` | ロック・回復後に同一Mac内へ完成した世代を作り、世代と検証結果を返す |
| `backup.restore_backup(backup_dir: Path, destination: Path) -> dict` | 空の復旧先へハッシュ検証付きで展開。元の稼働先を変更しない |

CLI案: `python3 -B -m scripts.activity_collection.cli --root <runtime> plan|import|status|read-day|backup|restore`。`plan --now <ISO日時>`、`import --input <JSONファイル>`、`read-day --date <日付>`、`restore --backup <世代> --destination <空フォルダ>` とする。通常のplanは現在時刻を使い、now指定はテスト・再現用。

出力はJSON。statusは本文・資格情報・実ハンドルを出さず、対象別名・期間・成功/部分/保留・件数のみ。read-dayだけが日記用の個人本文を返す。終了コードは0=処理成功、2=入力/設定不正、3=競合、4=回復・保存失敗。認証切れ等は保存できた収集結果のstatusで区別し、CLIの終了コードだけで取得成功と判断しない。

## 9. 受入確認

架空データで次を検証してから、合意した範囲の実機確認へ進む。

- 別日の同じ動画は別記録、同日の再読取は重複を増やさない。再生回数を捏造しない。
- 日時不明リポストの初回日を維持し、元投稿の日付を共有日へ流用しない。
- 読取ゼロの成功、部分取得、認証待ち、環境利用不能を区別する。
- 記録保存前・日別保存後・進捗保存後の各停止から回復し、取得範囲を先に進めない。
- 不正入力・パス逸脱・競合・壊れた進捗・異なる内容でのbatch ID再利用を拒否する。
- バックアップから空フォルダへ復旧し、初回取得日・本文・未取得範囲が一致する。

無人起動・復帰・認証の実機確認が残っていても、上記の保存処理と手動収集手順は独立して実装・検証できる。実際の起動経路を仮定したコードや、有効な定期実行設定は作らない。
