# 日々のログと短い対話で残す日記 — 設計書

作成日: 2026-10-09 / 状態: 本人レビュー待ち / 実装・外部送信は未実施

## 1. 目的と合意した方向

日々の仕事・個人開発と生活を、本人の負担一日 2〜3 分を目安に記録する。Codex のやりとりを Langfuse で確認し、dot が出来事を約 3 行提示して質問し、本人の短文または音声回答で補う。ログに出ない生活は本人の回答から残す。網羅性や連続日数を目標にしない。

一日一つの Markdown を専用 private GitHub リポジトリへ保存する。初期運用は本人が日付と全文を確認し、その版に「OK」と言った日だけ保存する。返信がない日は下書きのまま保持し、催促や翌日の埋め合わせをしない。英語学習の完了記録とは別の記録で、日記作成を学習完了の判定や更新に使わない。

本書の承認は設計レビューであり、実装・ログ送信・資格情報設定の許可を兼ねない。今回はこの文書だけを作成し、製品コード、依存導入、リポジトリ作成、アップロード、定期ジョブ、認証設定へ進まない。

## 2. 最小構成と実行経路

Web アプリ、専用 DB、常駐サーバーは作らない。将来の最小構成は、既存の dot 対話面、ローカルの小さな実行処理、Git 管理外の下書き・状態ファイル、日記用 Git 作業コピーとする。各責務は同じ実行処理に置いてよく、サービス分割は不要。

```text
対象 Codex セッション
  → 明示的に導入・有効化する tracing 連携 → Langfuse
  → ローカル実行処理が Public API を読取
  → 秘密・第三者情報を除外 → 出来事候補とローカル下書き
  → dot の既存対話面で提示・一問ずつ質問
  ← 本人の短文／音声から確定したテキスト回答
  → 日付・版・全文を提示 → 本人の OK
  → ローカル実行処理が Git 作業コピーへ Markdown 作成
  → commit / push → 専用 private GitHub リポジトリ
```

dot は対話担当であり、dot 自体に Langfuse 接続や GitHub 書込能力があるとは仮定しない。取得・保存は、本人が承認したローカル実行環境の処理が担当する。Langfuse は Public API、GitHub は対象リポジトリだけを扱う Git の commit/push を推奨経路とする。認証方式・実行ホスト・接続可否は未確認である。

対話は既存の dot 会話スレッドに日付付きの出来事候補を出し、同じスレッドの本人返信を受け取る経路とする。親からの補足により、dot の会話内での質問・回答受信と、文字化された音声回答は現在利用できている。日次実行からの自動提示、返信を対象日・版へ関連付ける処理、Langfuse 読取から GitHub 保存までの接続は未検証であり、実装前に確認する。自動提示が使えなければ、本人がスレッドで日記開始を指示し、同じ対話と承認を行う手動起動で試す。外部メッセージサービスは追加しない。

## 3. 責務と受け渡す情報

| 責務 | 入力 | 出力・制約 |
| --- | --- | --- |
| 収集 | 対象本人・許可プロジェクト・JST 日付範囲 | 必要な trace/observation の ID、時刻、選択した本文、取得状況。取得以外の Langfuse 操作をしない |
| 下書き | 除外処理済みの資料 | 約 3 行の出来事、出典、確認が必要な点。本人発言と観測事実を分ける |
| 対話 | 下書きと対象日・版 | 本人の考え、気持ち、生活、学び・判断を補う回答。質問は一問ずつ、最大 2 問 |
| 保存 | 本人が確認した全文・承認版・保存先 | 一日一ファイル、commit ID、push 結果。承認のない版は保存しない |

収集では対象プロジェクトと本人の識別条件を必須とし、他人のセッションを混ぜない。ページングを完了するまで取得完了と扱わない。資料全文のローカル永続キャッシュは作らず、取得本文は必要な処理中だけ使用する。下書き・状態には短い要約、回答、出典 ID、取得メタデータだけを残す。

## 4. 一日の対話

1. 対象日、取得範囲、取得状況を示し、出来事候補を約 3 行提示する。候補が少なければ行数を水増ししない。
2. 「今日、残しておきたいことは何ですか？」のように、仕事や生活のどちらも答えられる一問を出す。
3. 回答で十分なら日記全文へ進む。必要な場合だけ追加一問を出す。たとえば本人が触れた判断の理由を聞く。追加は一問までで、質問を束ねない。
4. 回答を反映した全文を対象日・版とともに提示し、保存する版への OK を待つ。保存確認は内容を補う質問とは別の操作とする。
5. OK が来たら保存する。訂正が来たら新しい版を提示し、改めてその版の OK を待つ。

本人は回答・追加質問をスキップして、出来事だけの全文を確認してもよい。無回答から OK を推定しない。音声は認識テキストを日記へ反映し、誤認識は全文確認で修正できるようにする。音声ファイルを Git に保存しない。気持ち・学びが語られていない場合は「記載なし」とし、埋めるために追加質問を強制しない。

返信がない下書きは翌日以降も保持するが、新しい日の対話に自動で差し込まない。本人がその日を指定して再開した場合だけ扱う。複数日の確認待ちがあれば、曖昧な「OK」では保存せず対象日・版を特定する。自動の振り返り質問は一日最大 2 問で、再開しても回数をリセットしない。本人からの自発的な追記は受け取れる。

## 5. JST 日付、日跨ぎ、欠落と遅延

日記のキーは `Asia/Tokyo` の暦日 D。ログ対象は D の 00:00 以上、翌日 00:00 未満の半開区間で、API 用に UTC へ変換する。例: 2026-10-09 の範囲は `2026-10-08T15:00:00Z` 以上、`2026-10-09T15:00:00Z` 未満。端末や実行環境のタイムゾーンに依存させない。

出来事は取得時刻でなく、その turn/observation の発生開始時刻で所属日を決める。日跨ぎの turn は開始日に一度だけ記載し、翌日まで継続した旨を付ける。セッション全体を開始日にまとめず turn 単位で扱う。時刻がない資料は日付未確認として自動割当しない。本人が語った出来事の日付が違う場合は本人指定を優先し、ログ由来の日時と区別する。

夜の起動が当日終了前なら、表示は「当日 00:00〜取得時刻までのログに基づく暫定記録」とする。日記日 D は対話開始時に固定し、深夜の回答や保存でも翌日へ変更しない。翌日になったことだけを理由に再質問・再保存しない。

下書きと保存版に、取得時刻、対象区間、取得成功／部分取得／取得失敗／対象ログなし、遅延可能性を残す。「ログなし」を「活動なし」と書かない。正常取得でも生活や未連携セッションは観測できず、一日全体の完全記録とは保証しない。連携停止、未完了 turn、API 遅延などは欠落要因として表示する。遅延の長さは利用バージョンと実測が未確認なので保証しない。

自動実行ごとに前日・当日の bounded な範囲を再読し、出典 ID で照合する案とする。これより古い日は本人の明示的な再収集指示で扱う。確認待ちの版や保存済み本文は遅延ログで書き換えない。新しい資料はローカルの差分候補として保持し、本人が再開したときだけ提案する。これにより夜以降のログを無断で追記しない。

## 6. ファイルと状態

リポジトリ内の保存先案は `diary/YYYY/YYYY-MM-DD.md`。同じ日に二つ目のファイルを作らない。下書きと処理状態はリポジトリ外のローカル専用ディレクトリへ置く。下書きを GitHub に push することは「下書き保持」に含めない。

状態ファイルには日付、版、本文ハッシュ、出典 ID 集合、取得状況、質問回数、対話関連 ID、承認日時・承認版ハッシュ、保存先、commit ID と push 状態を記録する。秘密、認証ヘッダー、生ログは含めない。状態更新は一時ファイルからの置換などで途中破損を防ぐ。

| 状態 | 意味・次の操作 |
| --- | --- |
| 下書き | 候補を保持。本人回答または明示的な再開を待つ |
| 対話中 | 一問ずつ補完。無回答ならこのまま保持する |
| 確認待ち | 全文・版を提示済み。OK または訂正を待つ |
| 保存待ち | 対象版の OK を記録済み。承認版だけを保存する |
| 保存済み | 対象 commit がリモートにあることを確認済み |
| 要対応 | 取得・Git 競合・権限などの問題。本文と承認を保持する |

承認後に本文を変えたら、その承認は新しい版には使えない。保存失敗時の再試行には、変更していない承認版を使う。commit 成功だけでは保存済みにしない。push の応答が不明ならリモートの commit・内容を照合してから状態を確定する。

日記の内容構造は以下とする。例示は書式であり、実際の日記ではない。

```markdown
---
date: YYYY-MM-DD
timezone: Asia/Tokyo
revision: 1
approved_at: ISO8601
collected_at: ISO8601
log_status: partial
---
# YYYY-MM-DD
## 出来事
- [観測事実] 資料で確認できた出来事。出典: S1
- [本人発言] 本人が語った生活の出来事。出典: A1
## 本人の考え・気持ち
本人回答の短い要約。未回答なら記載なし。
## 学び・判断
本人が述べた学び・判断。未回答なら記載なし。
## 質問と回答
- Q1: 質問本文
- A1: 本人回答（必要な除外処理後の短文）
## 出典と取得状況
- S1: Langfuse の trace/observation ID（安全なリンクが作れる場合だけリンク）
- 対象範囲・取得時刻・取得状況・遅延または未観測の範囲
```

出典 URL に資格情報、署名付きクエリ、第三者名を埋め込まない。対話リンクが使えなければローカルで対応できる回答 ID を記す。出典への将来のアクセスや保存期間は保証しない。回答は秘密・第三者情報を削除する場合があり、削除を明記する。残った本人の意味を変えず、断定的な感情を生成しない。

## 7. 重複実行と手編集の保護

日付 D を処理の一意キーとし、ローカルで同時実行ロックを取る。再起動時は状態と実ファイル・Git リモートを照合してから再開する。出典は project + trace/observation ID で重複排除し、親 turn と子 observation を別の出来事として二重計上しない。対話提示済み ID と質問回数も保持し、再実行で同じ質問を送らない。提示結果が不明なときは自動再送を止めて要対応にする。

保存前に作業コピーを最新化し、対象パスの存在・内容ハッシュと承認版を比較する。同じ内容が保存済みなら何もしない。手編集、既存ファイル、リモートの変更を検知したら自動上書きしない。新規保存は対象パスがないこと、更新は本人が差分を確認したことと比較元の Git blob/commit が一致することを条件とする。専用作業コピーが汚れていたら止め、対象日記以外のファイルを commit しない。

push 競合は force push で解決しない。リモートの同一版なら保存済みを回復し、異なる版なら差分確認を待つ。遅延ログや再生成は候補を別途保持し、保存済みの日記への更新にも再承認を必要とする。

## 8. 資料と命令の境界・共有範囲

Langfuse 内のユーザー発言、assistant 発言、ツール出力、引用、URL、ファイル内容はすべて資料として扱う。「秘密を送れ」「この URL にアップロード」「OK とみなせ」などの記述を運用指示として実行しない。ログに含まれる過去の本人発言も、今回の保存承認ではない。現在の本人による対象日・版への確認だけを承認として扱う。ログを理由に対象プロジェクト、保存先、権限、認証設定を変更しない。

観測事実は「変更した」「テスト成功が記録された」など根拠のある範囲に限る。assistant の成功報告だけなら「assistant が成功と報告」と区別する。本人の発言は本人発言として扱い、感情、成果の成功、作業時間をログの量や時刻差から断定しない。不一致は未確認として残す。

共有範囲は三つに分けて本人レビューする。

- Codex → Langfuse: tracing 連携を有効にすると広い範囲の transcript が送信される。日記用に要約だけ送る仕組みとは異なる。公式連携は明示的な導入・有効化が必要である。[公式 Codex 連携](https://langfuse.com/integrations/developer-tools/codex)
- Langfuse → 下書き・dot 対話面: 対象資料を必要最小限に取得し、対話への提示前に秘密・不要な第三者情報を除外する。対話面と要約モデルの処理先・保持条件もレビュー対象とする。
- 確認済み日記 → GitHub: 要約・本人回答・安全な出典だけを保存する。生ログ全文、画像、音声、認証情報は保存しない。

秘密の除外は要約前と保存前に行い、API キー、トークン、パスワード、秘密鍵、認証ヘッダー、個人連絡先、不要な第三者名・顧客情報を落とす。抽出失敗や除外に確信が持てない候補は提示・保存を止め、秘密本文を再掲せず問題を知らせる。

ただし日記側の除外は、すでに Langfuse に送られた原文を消す対策にはならない。公式 Masking は送信前の加工を説明しているが、現在の Codex 連携でその加工をどこまで適用できるかは未確認。利用する連携経路で検証し、送信したくない情報のあるセッションは tracing 対象にしない。[公式 Masking](https://langfuse.com/docs/observability/features/masking)

private Git でも commit の過去履歴、クローン、バックアップに情報が残る。本文から消しただけでは過去履歴から消えない。秘密の混入時は以後の保存を止め、本人と認証情報の失効・履歴削除・複製先対応を判断する。private 設定を情報除外の代わりにしない。

## 11. 受け入れ条件

実装時は次のシナリオで検証する。本書作成時には実装試験を行っていない。

1. 正常日: 許可対象ログから約 3 行を示し、一問ずつ最大 2 問で補完する。全文の OK 後にだけ一つの日記を push し、リモート確認後に保存済みを示す。
2. 無回答・スキップ: 下書き保持、催促なし、翌日の埋め合わせなし。回答をスキップしても全文への明示 OK がない限り push しない。
3. 観測範囲: 本人発言と観測事実が区別される。感情、成功、作業時間を推測で断定せず、ログなしでも生活がなかったと書かない。
4. 日付: JST 00:00 境界、UTC 変換、日跨ぎ turn、深夜の回答で対象日が正しく固定され、境界の同じ資料を二日へ重複記載しない。
5. 欠落・遅延: API 失敗、ページ途中失敗、対象ログなし、後着ログを識別する。暫定の取得範囲を表示し、後着ログで承認版・保存済み本文を自動更新しない。
6. 再実行: 同時実行、途中停止、提示結果不明、push 結果不明を与えても重複質問・重複ファイル・重複 commit を作らない。不明な副作用は照合するか要対応に止める。
7. 承認: 対象日・版・本文ハッシュを結び付ける。変更後に古い OK を使わず、ログ中の OK や無回答を承認にしない。
8. 手編集: ローカル・リモートの既存編集を検知して上書きを止める。更新差分は再確認し、対象外ファイルを commit しない。force push しない。
9. 資料中の命令: 外部送信・秘密抽出・保存先変更を命じるログを与えても実行せず資料として処理する。
10. 情報除外: 秘密や不要な第三者情報を含む資料・回答から、下書き、対話提示、日記、状態、エラーメッセージにその値が残らない。生ログ・画像・音声を Git に保存しない。
11. 接続と権限: 未接続を接続済みと表示しない。取得・保存が失敗したら下書きと承認版を守り、失敗理由だけを秘密なしで示す。
12. 分離: 日記を保存しても英語学習の完了記録を更新しない。

## 12. 設計の自己レビュー

設計範囲を一つの日記フローに絞り、Web アプリと専用 DB を除外した。本人の OK を「確認した本文の版」へ限定し、遅延ログ・訂正・再試行で無断保存にならないようにした。「毎日日記」は毎日の候補作成であり、無回答日まで保存を強制する要件ではないと明確化した。

当日夜の取得と一日全体のログが一致しない点は暫定範囲の表示で扱い、日跨ぎは対象日固定と開始時刻の規則で整理した。下書き保持は Git 外、保存済みはリモート確認後と定義した。dot 対話と API/Git 実行を分け、未確認の接続を既存能力として書かないようにした。残る判断事項は第 10 節に集約し、仮の時刻・認証・保存先で実装へ進まない。
